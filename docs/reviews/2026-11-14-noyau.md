I found several ways to obtain misleading verification results, plus durability failures that the passing tests do not cover. This is a static review of the specification, scoped implementation, contract, and tests; I did not modify files or rerun the write-producing test suite.

1. **High — Certificate-chain validation accepts non-CA certificates as issuers.**  
   [anchor.py:490](C:/Users/sawle/OneDrive/Desktop/ChargeGrinder/Empreinte/src/empreinte/anchor.py:490), [verify_bundle.py:353](C:/Users/sawle/OneDrive/Desktop/ChargeGrinder/Empreinte/tools/verify_bundle.py:353)

   `_chain_to_roots()` checks certificate signatures and validity dates, but not issuer `BasicConstraints.ca`, `KeyUsage.keyCertSign`, or path-length constraints.

   **Scenario:** Someone possessing an ordinary end-entity certificate and its private key, chaining to the supplied root, issues themselves a timestamping certificate. They sign a token with an invented date and embed the intermediate certificates. Both implementations can accept this as trusted, including with `--tsa-ca`. No trusted CA key needs to be compromised.

   **Fix:** Use a proper certificate-path validator, enforcing CA status, key usage, path length, applicable EKU constraints, and unsupported critical extensions. The documented exclusions for revocation, policies, and name constraints do not cover these missing basic checks.

2. **High — Default anchoring can accept a network attacker’s invented timestamp.**  
   [vault.py:174](C:/Users/sawle/OneDrive/Desktop/ChargeGrinder/Empreinte/src/empreinte/vault.py:174), [anchor.py:519](C:/Users/sawle/OneDrive/Desktop/ChargeGrinder/Empreinte/src/empreinte/anchor.py:519), [verify_bundle.py:458](C:/Users/sawle/OneDrive/Desktop/ChargeGrinder/Empreinte/tools/verify_bundle.py:458)

   The default transport is HTTP and the default trusted-root list is empty. A valid signature from the certificate supplied by the response is sufficient.

   **Scenario:** An HTTP intermediary reads the requested hash and nonce, generates its own TSA certificate with the required EKU, and returns a correctly signed token asserting an arbitrary date. `anchor()` stores it under the requested authority URL; `verify()` reports success. The standalone verifier assigns `anchored_at` without requiring `chain_trusted`; its JSON output omits the trust distinction altogether.

   The text-mode caveat helps, but “outside timestamp: yes, existed by … according to [URL]” still attributes an unauthenticated certificate to an unauthenticated URL.

   **Fix:** Authenticate the TSA by default using configured roots or a pinned identity. Keep “token signature valid” separate from “trusted timestamp,” and do not populate a proven date from an untrusted token.

3. **High — `proof()` returns forged anchor dates without checking the token.**  
   [vault.py:832](C:/Users/sawle/OneDrive/Desktop/ChargeGrinder/Empreinte/src/empreinte/vault.py:832)

   `proof()` checks the record chain, then selects anchors solely by sequence and head hash. It never calls `check_anchor()` before calculating `proven_before`.

   **Scenario:** A directory attacker changes an anchor’s `anchored_at` to 2000 while preserving its head hash, or inserts an anchor with a matching head and garbage proof. After reopening, `proof()` can return `verified=True` and `proven_before=2000`. A separate `verify()` would reject the token/date, but the proof API itself supplies the false date.

   **Fix:** Validate each candidate token and its trust before using its time. Return anchor-validation errors explicitly rather than presenting invalid dates as proven.

4. **High — Duplicate bundle items can replace missing licensed items and still pass.**  
   [verify_bundle.py:480](C:/Users/sawle/OneDrive/Desktop/ChargeGrinder/Empreinte/tools/verify_bundle.py:480)

   The verifier checks each item’s membership in a set and compares only the number of manifest items with the set’s size.

   **Scenario:** A valid grant licenses A and B. An intermediary replaces `manifest.items` with `[A, A]` and removes B’s plaintext. Both copies of A authenticate, both are listed in the grant, and `2 == len({A, B})`. The verifier prints `ALL CHECKS PASSED` although B is missing. No signing key is required.

   **Fix:** Reject duplicate item identities and compare the actual disclosed identities with the complete granted set. Define duplicate handling in `grant()` too: it currently accepts duplicate requests that its own verifier then rejects.

5. **High — Two vault instances can corrupt the ledger through ordinary successful writes.**  
   [vault.py:167](C:/Users/sawle/OneDrive/Desktop/ChargeGrinder/Empreinte/src/empreinte/vault.py:167), [vault.py:508](C:/Users/sawle/OneDrive/Desktop/ChargeGrinder/Empreinte/src/empreinte/vault.py:508)

   The lock belongs to one Python object. Sequence numbers and predecessor hashes come from that object’s cached ledger.

   **Scenario:** Processes A and B open the same head N. A appends N+1 successfully. B then appends its own N+1, pointing to N rather than A’s record, and overwrites the catalog with its stale state. Both calls can return successfully; reopening finds duplicate sequence numbers and a broken chain. Two objects in one process have the same problem.

   **Fix:** Enforce exclusive writer ownership and reload/check the current head while holding it. For independently synced replicas, explicitly detect divergent histories; local locking alone cannot serialize remote writers.

6. **High — `verify()` does not recheck the current on-disk ledger, header, catalog, or anchors.**  
   [vault.py:750](C:/Users/sawle/OneDrive/Desktop/ChargeGrinder/Empreinte/src/empreinte/vault.py:750)

   Verification uses `_header`, `_ledger.records`, catalog state, and `_anchors` loaded earlier. Only blob contents are reread.

   **Scenario:** After the vault opens, a sync client or directory attacker truncates `ledger.jsonl`, changes `header.json`, or deletes `anchors.jsonl`, leaving blobs intact. Calling `verify()` on that object can still return `ok=True`. This violates the API’s promise to “re-check” the stored chain and anchors.

   **Fix:** Read and validate a coherent disk snapshot during verification, without repairing it. Coordinate this with writer synchronization so verification cannot mix generations.

7. **High — Failed appends can leave the live object able to deepen corruption.**  
   [vault.py:552](C:/Users/sawle/OneDrive/Desktop/ChargeGrinder/Empreinte/src/empreinte/vault.py:552), [store.py:78](C:/Users/sawle/OneDrive/Desktop/ChargeGrinder/Empreinte/src/empreinte/store.py:78)

   `_flush()` clears `_pending_records` **before** appending them. There is also no recovery state for an append that writes some or all bytes and then fails during flush/fsync.

   **Scenario:** A batch contains two in-memory records. Disk-full causes its append to fail. The pending list is now empty, but the records and catalog entries remain in memory. After space is freed, `lock()` can persist a catalog claiming records that were never written. Alternatively, an ordinary append writes a complete line but fsync fails; the next `put()` reuses that sequence because the in-memory append never happened.

   **Fix:** Treat append failures as an uncertain commit outcome. Disable further mutations until the file has been reread and reconciled. Preserve pending state until success, but do not blindly retry an append that may already have reached disk.

8. **Medium — The advertised all-or-nothing batch crash guarantee is not implemented, and batch blob names are not durably synced on POSIX.**  
   [vault.py:532](C:/Users/sawle/OneDrive/Desktop/ChargeGrinder/Empreinte/src/empreinte/vault.py:532), [store.py:41](C:/Users/sawle/OneDrive/Desktop/ChargeGrinder/Empreinte/src/empreinte/store.py:41), [FORMAT.md:250](C:/Users/sawle/OneDrive/Desktop/ChargeGrinder/Empreinte/docs/FORMAT.md:250)

   **Scenarios:**
   - A crash during the multi-line append leaves several complete records followed by a torn record. Recovery retains and replays the complete prefix. There is no batch boundary or commit marker, so it cannot discard the whole batch as documented.
   - Batch blobs use `durable=False`; the eventual flush fsyncs files but not their containing directories. On POSIX, a power failure can lose renamed blob directory entries after the ledger has become durable. Newly created shard directories also require parent-directory synchronization.

   **Fix:** Either document prefix-commit semantics or implement a recoverable batch transaction marker. Fsync affected directories, including newly created directory ancestry, before committing records that reference their blobs.

   Separately, a Python exception inside `batch()` intentionally commits completed operations through `finally`; it is not a rollback transaction.

9. **Medium — `lock()` leaves secrets reachable when flushing fails.**  
   [vault.py:348](C:/Users/sawle/OneDrive/Desktop/ChargeGrinder/Empreinte/src/empreinte/vault.py:348)

   `_flush()` executes before `_drop_keys()` with no cleanup `finally`.

   **Scenario:** Inside a batch, or after a catalog-write failure, the user locks the vault while the disk is full/read-only. Flush raises, leaving `_master`, `_keys`, `_signer`, recovery text, and decrypted catalog state attached to the object. This is retained live state, beyond the documented limitation that Python cannot wipe freed memory.

   **Fix:** Guarantee secret-reference removal even when persistence fails, while surfacing the durability failure. If a separate “save before locking” operation is needed, distinguish it from the security operation of locking.

10. **Medium — Opening an inconsistent vault does not reliably disable writes.**  
    [vault.py:437](C:/Users/sawle/OneDrive/Desktop/ChargeGrinder/Empreinte/src/empreinte/vault.py:437), [vault.py:498](C:/Users/sawle/OneDrive/Desktop/ChargeGrinder/Empreinte/src/empreinte/vault.py:498)

    `_recover()` returns immediately when record counts agree. It does not validate the existing chain; `_require_writable()` checks only `_open_problems`, excluding ledger parse problems and errors later returned by `verify()`.

    **Scenario:** An attacker alters an earlier record’s signature, preserving record count and the stored final hash. The vault opens writable. `verify()` reports the invalid signature, but `put()` still succeeds afterward. An added unreadable line can similarly leave `Ledger.problems` populated without blocking writes.

    **Fix:** Establish a validated writable state during open, including parse problems, chain/signatures, identity consistency, and relevant anchor/catalog checks. Integrity failures must invalidate that state. This is explicitly promised by FORMAT §9.

11. **Medium — Bundle-controlled paths escape the bundle directory.**  
    [verify_bundle.py:465](C:/Users/sawle/OneDrive/Desktop/ChargeGrinder/Empreinte/tools/verify_bundle.py:465), [verify_bundle.py:489](C:/Users/sawle/OneDrive/Desktop/ChargeGrinder/Empreinte/tools/verify_bundle.py:489)

    Grant and item paths are joined directly to `bundle`, without containment checks.

    **Scenario:** Change an unsigned manifest path to `../other-copy/item.txt`, an absolute path, or a symlink leading outside. If that external file contains the committed bytes, verification passes despite the bundle not containing the document. Malicious paths can also cause reads from devices, blocking streams, or Windows network shares.

    **Fix:** Require relative paths, resolve them beneath the bundle root, reject escapes and unsuitable file types, and address symlink races where relevant. Apply the same policy to every referenced artifact.

12. **Medium — Unauthenticated inputs can demand unbounded memory or work.**  
    [crypto.py:70](C:/Users/sawle/OneDrive/Desktop/ChargeGrinder/Empreinte/src/empreinte/crypto.py:70), [anchor.py:68](C:/Users/sawle/OneDrive/Desktop/ChargeGrinder/Empreinte/src/empreinte/anchor.py:68), [verify_bundle.py:397](C:/Users/sawle/OneDrive/Desktop/ChargeGrinder/Empreinte/tools/verify_bundle.py:397)

    KDF parameters have no resource bounds before Argon2 runs. HTTP responses, manifests, item files, token certificate collections, and chain-digest arrays are also loaded without limits.

    **Scenario:** A directory attacker raises Argon2 memory or iteration counts; merely attempting unlock exhausts memory or occupies the process before authentication can reject the header. A malicious bundle or HTTP responder can likewise supply oversized input.

    **Fix:** Validate KDF types and supported resource ranges before derivation. Bound metadata/token sizes and collection counts; stream plaintext hashing and impose an explicit large-file policy. KDF associated data prevents successful downgrade authentication, but cannot prevent this pre-authentication resource attack.

13. **Medium — RSA-PSS token verification ignores the encoded algorithm parameters.**  
    [anchor.py:465](C:/Users/sawle/OneDrive/Desktop/ChargeGrinder/Empreinte/src/empreinte/anchor.py:465), [verify_bundle.py:339](C:/Users/sawle/OneDrive/Desktop/ChargeGrinder/Empreinte/tools/verify_bundle.py:339)

    Both implementations infer the PSS hash and MGF hash from `digest_oid` and accept any salt length through `PSS.AUTO`, ignoring `RSASSA-PSS-params`.

    **Scenario:** A legitimate token specifying a different supported MGF1 hash is rejected. Conversely, a token whose declared salt length disagrees with its actual signature may pass. Verification is not checking the signature algorithm the token declares.

    **Fix:** Parse and enforce the PSS parameters, defaults, and trailer field, or explicitly reject unsupported parameter combinations. Add independent PSS fixtures; the existing OpenSSL fixture exercises PKCS#1 v1.5.

14. **Low — Catalog format versions are silently ignored.**  
    [vault.py:405](C:/Users/sawle/OneDrive/Desktop/ChargeGrinder/Empreinte/src/empreinte/vault.py:405)

    `_load_catalog()` never checks `format_version`.

    **Scenario:** A future writer produces a catalog using changed semantics but retaining recognizable fields. This reader accepts it and can overwrite it using version-1 semantics, rather than refusing as FORMAT §14 requires.

    **Fix:** Check the decrypted catalog’s version before interpreting any fields.

15. **Low — The timestamp specification gives conflicting message-imprint instructions.**  
    [FORMAT.md:299](C:/Users/sawle/OneDrive/Desktop/ChargeGrinder/Empreinte/docs/FORMAT.md:299), [anchor.py:276](C:/Users/sawle/OneDrive/Desktop/ChargeGrinder/Empreinte/src/empreinte/anchor.py:276)

    The prose says the imprint is “SHA-256 of our head hash.” The implementation and request diagram instead use the raw 32-byte head hash as `hashedMessage`, with SHA-256 as the algorithm identifier.

    **Scenario:** An independent implementer follows the prose and hashes the head again, producing incompatible requests or rejecting valid bundles.

    **Fix:** State consistently: `hashedMessage = bytes.fromhex(head_hash)`; it is already the SHA-256 digest of `prev_hash || body_digest`.

What I checked and found correct, subject to the findings above:

- Fresh per-blob salts, HKDF purpose separation, random nonces, and AEAD bindings protect against cross-vault/type/entry/version swaps. I found no practical nonce/key-reuse defect.
- Passphrase-wrap associated data includes the KDF object; changing its parameters does not yield a successful weaker unwrap.
- Salted commitments prevent offline plaintext guessing from the public ledger. Public metadata leakage is substantially described accurately.
- The two-level hash construction supports digest-only chain proofs. The standalone verifier recomputes disclosed record bodies, commitments, predecessor links, final head, and signatures; ordinary plaintext/salt changes, foreign-key records, and incomplete head proofs fail.
- Token checks bind the imprint, signed content digest, content type, signer certificate, and request nonce. DER parsing rejects indefinite lengths, truncated declared contents, and trailing bytes.
- Local-clock backdating and whole-snapshot rollback are honestly acknowledged. Same-slot aux replay is also possible, as expected for an unversioned cache; freshness is not authenticated.
- Replaying an old header restores old credential wraps because the master key is unchanged. Password/recovery rotation therefore does not revoke access against retained old headers; this limitation deserves explicit documentation.
- Normal crash recovery authenticates and verifies appended records before replaying their blobs. The existing tests cover these ordinary paths, but not concurrent writers, uncertain append failures, duplicate-item substitution, non-CA issuers, or forged dates returned by `proof()`.
